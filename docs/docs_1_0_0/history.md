## 2. 早期方案：自适应多级弧形分桶

历史材料中最早的完整设计是 **自适应多级弧形分桶排序（AMLABS）**。

核心想法：

- 用 `x_min`、`x_peak`、`x_max` 三个锚点构造两段折线桶函数；
- `x_peak` 表示分布峰值位置；
- 用 `m_peak` 控制峰值附近的桶密度；
- 桶内递归细分；
- 小桶插入排序；
- 最坏交给比较排序。

当时的设计包含：

```text
g(x) = 分段折线
继续细分 = m_b > τ 且 span_b > α * width_b
B = m / 4
索引表 + gather
```

## 3. 早期方案的评审结论

后续评审指出该方案存在结构性问题：

1. **自适应判据方向错误**
   - 数据挤在桶的一小段，`span/width` 很小；
   - 原判据却认为“已摊开”，停止细分；
   - 大桶直接插入，可能退化为 O(m²)。

2. **`B` 与复杂度分析不一致**
   - 伪代码 `B = m/4`；
   - 复杂度分析却按 `B=4` 估算递归层数；
   - 两者不是同一套参数。

3. **索引表 + gather 不可行**
   - gather 会改写原数组；
   - 先前记录的其他桶下标会失效；
   - 正确做法是两遍计数 + 前缀和 + scatter。

4. **折线桶函数分辨率不足**
   - 两段直线只能表达“左半段一个宽度、右半段一个宽度”；
   - 对单峰/偏态分布无法真正贴近密度；
   - 更接近等频分桶的思路需要经验 CDF。

5. **成本表漏项**
   - 桶内 `span` 扫描；
   - 桶表初始化；
   - 空桶遍历；
   - gather 的随机读写。

结论：弧形方案保留为历史设计，不进入当前实现。

## 4. 转向等宽 key 分桶

当前实现放弃了弧点、`m_peak`、`span/width`、索引表 gather，改为：

```text
值 -> 保序 uint64_t key
B = min(m, bucket_limit)
bucket = floor((key - min_key) * B / (max_key - min_key))
count
prefix
scatter 到 buf
copy 回原数组
组内递归/插入/fallback
```

关键变化：

- 不再估计峰值；
- 不再存原始下标；
- 不再用索引表 gather；
- 用前缀和直接给出每组起点；
- 桶号只依赖 key 的单调性；
- 桶数有硬上限，避免表过大。

## 5. 参数演化

当前默认：

```text
small_top      = 48
small_sort     = 16
leaf_sort      = 22
scan_threshold = 256
max_depth      = 16
bucket_limit   = 65536
```

演化要点：

- 顶层 `small_top` 与核心 `small_sort` 分离，避免把核心组 22~47 推给 fallback；
- 小 n 使用插入 fallback；
- `leaf_sort=22` 来自插入与再分桶的交叉区间；
- `bucket_limit` 从“按 n 自动 64K/1M”收敛为默认 64K，控制缓存和并行表内存；
- `scan_threshold=0` 定义为关闭嵌套扫描。

## 6. 并行演化

并行实现经历了两步：

1. 只并行 root count/scatter/copy；
2. 增加 depth=1 组并行。

当前并行结构：

```text
root 并行 count
  -> 合并局部计数
  -> 计算每线程每桶起点
  -> 并行 scatter
  -> 并行 copy
  -> depth=1 组并行
```

内存控制：

- 每线程计数表上限 `max_buckets=65536`；
- 组 scratch 由 `scratch_budget` 限制；
- 大组时自动降低组并发。

## 7. 已尝试但未进入当前实现的方向

历史材料中还记录过：

- 固定扇出桶中桶；
- offset 表/多级 offset；
- 均值居中桶域；
- 预计算 key/pair；
- 纯 double 数值桶映射；
- 与 TimSort 的结构化数据竞争。

这些方向的共同问题：

- 额外一遍 n 的扫描；
- 额外表/offset 内存；
- 随机写增加；
- 对结构化数据仍无法保留 run；
- 收益不足以抵消复杂度。

当前实现不包含这些分支。

## 9. 当前定位

当前实现对随机/平滑数值分布有优势；对结构化数据明确让位给 TimSort。

历史演化得到的结论：

> 分布排序的优势来自“值域可直接计算”，  
> 劣势来自“第一次 scatter 会切断原始 run”。  
> 这两点在当前架构内不可同时消除。
